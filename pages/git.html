Git：版本历史，不是命令魔法

每次命令前先问：它会改哪里？为什么现在做？变化接着会去哪里？

01 Git、GitHub 与核心心智模型

快速理解

没有 Git 时，项目容易出现 project-v1、project-final-real-2。Git 是分布式版本控制系统：它让一个项目有可读历史，能回看、比较和安全试验。Git 是电脑上的工具；GitHub 是托管 Git repository 的在线平台，二者不是同一个东西。

Repository（repo）是 Git 追踪的项目文件夹；隐藏的 .git 保存历史，不要手动修改。暂存区的价值是：你可以只选择已完成的改动进入一个 commit，而不是把所有未完成工作混在历史中。

先看文件所处的位置

你编辑 index.html
        │
        ▼
Working Directory（工作区）
“文件已经改变”
        │
        │ git add index.html
        ▼
Staging Area（暂存区）
“把这次改变选进下一个快照”
        │
        │ git commit -m "..."
        ▼
Local Repository（本地仓库）
“一个本地版本已保存”
        │
        │ git push
        ▼
Remote / GitHub（远程仓库）
“本地版本已同步到远程”

工作区是电脑上正在编辑的项目文件；暂存区是“下一次 commit 要包含哪些改动”的清单；本地仓库保存 commit 历史；remote 是另一台位置上的仓库，GitHub 是常见的托管地点。main 通常是主分支名称；origin 是这个远程地址常用的本地昵称。

02 本地工作：初始化、检查、暂存与提交

cd project
git init
git status
git add index.html
git add .
git commit -m "Add responsive navigation"
git log --oneline

用 status 判断“我现在在哪里？”

git status 不是“下一步命令”，而是状态检查。
│
├── Untracked：文件存在，但 Git 尚未开始追踪它
├── Modified：已追踪文件在工作区被改过
├── Staged：改动已选入下一次 commit
└── Clean：没有待提交改动

不确定时：先 status，再决定下一步。

同一个 index.html 的三次状态变化

编辑后
Working Directory：index.html = modified
        │
        │ git add index.html
        ▼
Staging Area：index.html = staged
        │
        │ git commit -m "Update navigation"
        ▼
Local Repository：一个本地 commit 已保存

git add 不等于 commit，也不等于上传。
git commit 不等于 GitHub 上传。
只有 git push 才会同步已存在的本地 commit 到远程。

add 前：改动只在工作区。add 后：它已被选进下一快照；还没有创建 commit，也没有上传。commit 后：历史已保存到本机；GitHub 仍可能没有这个 commit。通常下一步是用 git status 检查，确认后再 git push。

命令 做什么 / 何时用 安全级别
git init 在项目文件夹内运行一次，创建 .git。 ◇基础 / 可安全练习
git status 问“现在是什么状态？”它显示 Untracked、Modified、Staged 或 Clean。不确定下一步时，先 status。 ◇基础
git add 把改动放入 Staging Area，准备下一个 commit；它不是上传。git add . 前先看 status/diff。 ◇基础
git commit -m 在本地保存带说明的快照，只记录 staged 内容。消息写一个清楚变化，例如 Fix calculator clear button，不要只写 update/stuff/final。commit 不等于 GitHub。 ◇基础
git log 查看 commit 历史；--oneline 用于简洁总览。 ◇基础

03 远程仓库、origin 与同步

git remote -v
git remote add origin URL
git push -u origin main
git fetch
git pull
git clone URL

remote 是远程仓库的连接信息；origin 不是 GitHub 本身，而是远程地址常用的昵称。git remote add origin URL 是告诉本机 Git“把这个 URL 叫 origin”。push 将本地提交发送到 remote；-u 设 upstream，之后常可直接 git push。由于 push 会改变共享远程状态，属于 🟡 先理解再做。

clone URL 是第一次完整复制一个 repo，clone 不等于 pull。fetch 下载远程信息但不直接整合当前工作；pull 通常是获取并整合。已有 remote 时不要重复添加 origin；先用 git remote -v 看连接。.gitignore 可列出不应提交的文件，例如 .DS_Store、node_modules/、可能含秘密的 .env；已被追踪的文件后来加入 ignore 不会自动停止追踪。

04 分支、main、合并与冲突

main: A---B---C
              \
feature:       D---E

git branch
git switch -c feature-navbar
git switch main
git merge feature-navbar

branch 是独立开发线，不是复制项目文件夹。git branch 查看分支，git branch feature-name 创建；推荐 git switch branch-name 切换，git switch -c new-branch 创建并切换。旧教程可能写 checkout。main 通常是主分支名称，不等于 Git。merge 把 feature 的提交整合进当前分支。

冲突不是失败

当同一文件同一位置有不同修改，Git 无法替人选择。阅读冲突内容，选择正确版本，删除 <<<<<<<、=======、>>>>>>>，测试，再 git add 与 git commit。冲突是在请求人做决定。

05 先检查，再恢复：安全边界

git status
git diff
git diff --staged
git restore filename
git restore --staged filename

diff 看未暂存改动；diff --staged 看将进入 commit 的内容。git restore --staged filename 只撤销暂存，保留工作区改动；git restore filename 会丢弃该文件未提交修改，执行前必须读 diff 和确认目标。HEAD 是“我现在在哪里”，通常指当前分支的当前 commit。

🔴 危险 / 破坏性

git reset --hard 可能永久丢失未提交修改；git push --force 可重写共享远程历史。本页仅为识别风险而列出它们：未充分理解、确认目标和备份时，不要执行。

06 初学者工作流

第一个 GitHub 项目

mkdir project
cd project
git init
git status
git add .
git commit -m "Initial commit"
git branch -M main
git remote add origin URL
git push -u origin main

这不是一段应盲目粘贴的魔法：git init 让当前文件夹成为有本地历史的 repository；第一次 git commit 才创建本地版本；git branch -M main 把当前分支命名为 main；git remote add origin URL 给远程仓库地址一个本机昵称 origin；最后 git push -u origin main 才把本地 main 的 commit 发送到远程，并记住这条对应关系，方便之后直接 git push。

第一次 push 前
├── 本地仓库：已有至少一个 commit
├── 当前分支：main
└── remote：origin 已指向正确 URL
        │
        │ git push -u origin main
        ▼
第一次 push 后
├── 远程仓库：收到 local main 的 commit
└── upstream：local main 与 origin/main 已建立对应

push 改变共享远程状态（🟡 先理解再做），但不会替你创建 commit。

日常工作

git status
# edit code
git diff
git add .
git status
git commit -m "Describe one clear change"
git push

每步都有目的：知道状态 → 修改 → 看实际变化 → 选择进快照 → 确认暂存内容 → 保存本地历史 → 共享。已有 clone 的项目，开始前先 git pull；要单独开发功能，git switch -c feature-navbar，完成后切回 main、merge、再 push。

07 常见问题与真实项目经验

src refspec main does not match any

已有项目经验表明：常见原因是还没有 first commit，或当前 branch 状态不是 main。不要随机粘贴命令。依次执行：git status → 确认需要追踪的文件 → git add . → git commit -m "Initial commit" → git branch → 必要时 git branch -M main → git push -u origin main。每一步都先确认当前 Git state。

症状：src refspec main does not match any
        │
        ▼
发生了什么？Git 找不到可发送的 local main 内容。
        │
        ▼
为什么？常见原因：还没有 first commit，或当前分支不是 main。
        │
        ▼
心智模型：push 只能发送已经存在的本地 commit；它不会创造 commit。
        │
        ▼
修复：先 status 确认状态，再 add → commit → branch → 必要时命名 main → push。
        │
        ▼
避免：每一步先检查状态，不随机粘贴修复命令。
  • fatal: not a git repository：先确认当前目录。
  • remote origin already exists：昵称已经存在，用 git remote -v 检查。
  • rejected/non-fast-forward：remote 有你还没整合的历史；先理解 pull/fetch 和冲突。
  • nothing to commit：没有新的 staged 改动；用 status/diff 看原因。
